# DATABASE_MIGRATION_AUDIT — KEYONE

**Date:** 2026-06-12
**Scope:** Current DB architecture, SQLite risks, the PostgreSQL migration path, backup/restore strategy, and downtime estimates.

---

## 1. Current database architecture

| Property | Value |
|---|---|
| Engine | **SQLite** (`provider = "sqlite"` in `saas/prisma/schema.prisma`) |
| Connection | `DATABASE_URL` (Prisma); `lib/db.ts` prefers `DATABASE_DIRECT_URL` if set |
| File path (live) | `C:/KEYONE/data/saas.db` *(deploy template)* **or** `C:\app\saas\prisma\prod.db` *(backup script)* — ⚠️ reconcile which is authoritative |
| Schema size | 1,678 lines, **64 models** |
| Schema management | **`prisma db push`** — **no `prisma/migrations/` directory exists**; there is no versioned migration history |
| Journaling | WAL mode applied at boot in `lib/db.ts` (`PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`), fire-and-forget |
| Client | Prisma singleton (`global.prisma ?? createClient()`); direct file I/O, **no connection pool, no Redis dependency** |
| Postgres target | `saas/prisma/schema.postgres.prisma` (generated by `scripts/generate-pg-schema.sh`), `provider = "postgresql"`, pooled `POSTGRES_URL` + `directUrl POSTGRES_DIRECT_URL` |

**Data domains in the DB:** users/auth, team members, bots, customers + memory, conversations + messages, orders/commerce, subscriptions/plans, WhatsApp message ledger + templates + consent, safety/anti-ban state, usage ledgers, automations, audit logs, and **encrypted tenant provider credentials** (`TenantProviderCredential`, `Bot.aiApiKeyEnc`, `Bot.metaAccessTokenEnc`).

## 2. SQLite risks

| # | Risk | Severity | Detail |
|---|---|---|---|
| R1 | **Single-writer bottleneck** | High at scale | One writer at a time. At ~25–50 concurrent merchants, `SQLITE_BUSY` errors cascade (per capacity report). Fine today (small tenant count). |
| R2 | **No point-in-time recovery** | High | Recovery granularity = last file backup (daily). Up to ~24h data loss window (RPO) with current daily backup. |
| R3 | **WAL sidecar files** | Medium | A live copy must include/checkpoint `*.db-wal` and `*.db-shm`, or the copy may be stale/inconsistent. Use `sqlite3 .backup` (online) — which `backup-db.ps1` already does. |
| R4 | **No migration history** | Medium | `db push` means no `migrate deploy` audit trail. Schema is reproduced from `schema.prisma`, but historical schema states aren't versioned. |
| R5 | **File corruption on crash/disk** | Low prob / High impact | A single file; corruption or disk loss without an off-site backup = total data loss. |
| R6 | **Backups are VPS-local only** | **Critical** | Daily DB backups write to `C:\app\backups` on the same disk. A VPS/disk loss destroys production **and** its backups together. |
| R7 | **Cross-OS portability** | Low | SQLite file is portable across OS; only the Prisma **query engine** is platform-specific (`prisma generate` on target). |

## 3. PostgreSQL migration path

**Status:** code-ready, **not executed**. Production still runs SQLite. The recommended trigger is ~20–25 concurrent merchants, or when HA / PITR / horizontal scale is needed.

### Pre-flight (do before cutover)
1. **Schema parity:** regenerate `schema.postgres.prisma` via `bash saas/scripts/generate-pg-schema.sh`; run `npm run verify:schema-parity`.
2. **Raw SQL sweep:** grep for any raw SQL / `$queryRaw` and check SQLite-isms (`LIKE` case sensitivity vs Postgres `ILIKE`, boolean/int coercion, `datetime()` functions).
3. **Provision Postgres:** Supabase (recommended — managed, PITR, pooler) or self-hosted PG 15+.

### Migration steps
```bash
# 1. Stand up Postgres, set env
export POSTGRES_URL="postgresql://user:pass@host:6543/postgres?pgbouncer=true"
export POSTGRES_DIRECT_URL="postgresql://user:pass@host:5432/postgres"

# 2. Create the schema on Postgres (direct URL, no pooler)
cd saas
cp prisma/schema.postgres.prisma prisma/schema.prisma   # or use --schema flag
npx prisma db push --schema prisma/schema.postgres.prisma

# 3. Copy data SQLite -> Postgres
#    Option A: pgloader (fast, handles type coercion)
pgloader ./prisma/prod.db postgresql://user:pass@host:5432/postgres
#    Option B: a Prisma ETL script (model-by-model copy) — safer for FK ordering

# 4. Verify row counts match per table; spot-check encrypted columns decrypt
#    (AUTH_SECRET unchanged => Bot.aiApiKeyEnc still decrypts)

# 5. Swap env on the app: DATABASE_URL/DATABASE_DIRECT_URL -> Postgres, rebuild
```

### Cutover (maintenance window)
1. Stop intake: pause WhatsApp send queue + cron jobs.
2. Final delta sync (re-copy rows changed since the bulk load), or do the whole copy inside the window if the DB is small.
3. Point `DATABASE_URL`/`DATABASE_DIRECT_URL` at Postgres, deploy build with `schema.postgres.prisma`.
4. Smoke test: login, dashboard, send a test WA message, AI reply.
5. Resume cron + queue.

### Rollback
- **The SQLite file is never modified during migration.** Rollback = revert `DATABASE_URL` to the SQLite path, restore `schema.prisma` (sqlite), rebuild, restart. Near-instant.

## 4. Backup strategy (database)

| Mechanism | What | Where | Retention | Schedule |
|---|---|---|---|---|
| `backup-db.ps1` | online `sqlite3 .backup` → gzip | `C:\app\backups\prod-<ts>.db.gz` | 14 days | daily 03:30 (`KEYONE-DB-Backup`) |
| `backup-all.ps1` | DB + WA sessions + `.env` + prisma + uploads(if any) | `C:\app\backups\pre-deploy-<ts>\` | none (manual) | before each deploy |
| `verify-backup.ps1` | gunzip + `PRAGMA integrity_check` + `SELECT COUNT(*)` on `User`/`Bot` | n/a | n/a | recommended daily 04:00 |

**Gap:** no off-site replication, no PITR. See [BACKUP_POLICY](BACKUP_POLICY.md) for the recommended 3-2-1 policy. Post-Postgres, Supabase provides managed daily backups + PITR, replacing the manual gzip rotation.

## 5. Restore strategy (database)

**SQLite restore (to same or new server):**
```powershell
# Windows
nssm stop mse-saas
$gz = "C:\app\backups\prod-20260612-0330.db.gz"
# decompress
$in=[IO.File]::OpenRead($gz); $out=[IO.File]::Create("C:\KEYONE\data\saas.db")
$gzs=New-Object IO.Compression.GzipStream($in,[IO.Compression.CompressionMode]::Decompress)
$gzs.CopyTo($out); $gzs.Close(); $out.Close(); $in.Close()
nssm start mse-saas
```
```bash
# Linux / Docker target
gunzip -c prod-20260612-0330.db.gz > /var/keyone/data/saas.db
docker compose -f docker-compose.production.yml restart keyone-saas
```
**Then:** verify with `GET /api/health` (expects `db:ok`) and confirm `AUTH_SECRET` matches the backup era so encrypted columns decrypt.

**Validate before trusting a restore:**
```bash
sqlite3 saas.db "PRAGMA integrity_check;"        # expect: ok
sqlite3 saas.db "SELECT COUNT(*) FROM User;"      # sanity
sqlite3 saas.db "SELECT COUNT(*) FROM Bot;"
```

## 6. Downtime estimate

| Operation | Downtime | Notes |
|---|---|---|
| DB restore (SQLite, same server) | **1–3 min** | stop service → swap file → start |
| Full server rebuild + DB restore (Ubuntu) | **30–90 min** | provision + deploy + restore + DNS — see [DISASTER_RECOVERY](DISASTER_RECOVERY.md) Scenario A |
| SQLite → Postgres cutover (small DB) | **10–30 min** | maintenance window; data copy dominates |
| Postgres rollback to SQLite | **< 5 min** | env revert + rebuild; SQLite untouched |
| Routine code deploy (current Windows) | **8–12 min** | 502 window during `npm ci` + `next build` (502 incident report). Docker path would cut this to ~30s. |

---

## 7. Recommendations

1. **Add off-site DB backup immediately** (highest priority — closes R6). Even a daily `scp`/rclone of the gzipped DB off the VPS turns "total loss" into "≤24h loss."
2. **Confirm and document the single authoritative DB path** (`saas.db` vs `prod.db`).
3. **Shorten RPO** by increasing backup frequency (e.g. hourly `sqlite3 .backup`) until Postgres+PITR lands.
4. **Plan the Postgres migration** before crossing ~20 concurrent merchants (R1). The code is ready; the work is data copy + verification + a short window.
5. **Keep `AUTH_SECRET` backed up with the DB** — a DB restore without it loses all encrypted provider keys.
